Visual Search

Visual search lets shoppers find products by uploading a photo instead of typing keywords. A shopper taps the camera button in the search bar, selects an image (or takes one on mobile), and sees products that visually match what is in the photo.

Prerequisites

Visual search is a v2 Pathways API feature. Your Discovery account must have:

  • A visual search widget configured in the Discovery Dashboard
  • The Pathways auth key (authKey / auth_key) provisioned — this is the same v2 key used by recommendation widgets

Ensure your Discovery config has authKeyEnvVar (or authKey) set. See 12-credential-injection.md for credential resolution order.

How it works

Shopper clicks camera button
  → File picker opens
  → Image POSTed to POST /_brxdis-api/visual-search/{widgetId}/upload  (server-side proxy)
  → Plugin receives imageId from Discovery
  → Browser redirects to results page: ?imageId={id}&widgetId={id}
  → DiscoverySearchGridComponent detects imageId parameter
  → Calls Discovery Pathways visual search API directly
  → Products returned as normal product grid (dataSourceMode = "visual-search")

The upload URL /_brxdis-api/visual-search/{widgetId}/upload is generated by DiscoverySearchInputComponent and is the standard path. Your HST mount for BrxdisVisualSearchPipeline must be at /_brxdis-api nested under the channel mount — see Mount placement below.

Credentials are added server-side by the plugin — the Discovery API key is never exposed to the browser.

Channel Manager setup

Visual search is configured per-channel in Channel Settings → Visual Search:

Field Type Default Description
discoveryVisualSearchEnabled boolean false Enables the camera button in brxdis-search-input.ftl and sets visualSearchEnabled=true on the search input models.
discoveryVisualSearchWidgetId String "" The Discovery visual search widget ID from your Discovery Dashboard. Must be set when enabled.

Both fields live on DiscoveryChannelInfo. They apply to the entire channel (all pages/mounts sharing that channel).

If discoveryVisualSearchEnabled is true but discoveryVisualSearchWidgetId is blank, the plugin logs a warning and falls back to normal keyword search — no 500, no broken page.

Component setup

No additional component parameters are needed. The same DiscoverySearchGridComponent and brxdis-search-input.ftl that handle keyword search also handle visual search.

The search input template checks visualSearchUploadUrl to decide whether to render the camera button:

<#if (visualSearchUploadUrl!"")?has_content>
  <button type="button" class="brxdis-sb__vs-btn" id="brxdis-vs-cam-btn" title="Search by image">
    ...
  </button>
</#if>

The visualSearchUploadUrl model is only set when both discoveryVisualSearchEnabled=true and a widget ID is resolved — so the button is automatically absent on channels where visual search is off.

Models

Search Input component (DiscoverySearchInputComponent)

Key Type Description
visualSearchEnabled Boolean true when enabled for this channel.
visualSearchUploadUrl String Upload endpoint URL (e.g. /_brxdis-api/visual-search/{widgetId}/upload). Present only when enabled + widget ID resolved.
visualSearchWidgetId String The resolved widget ID. Present only when enabled + widget ID resolved.

Search Grid component (DiscoverySearchGridComponent)

When a visual search request is detected (imageId + widgetId URL params present):

Key Type Description
dataSourceMode String "visual-search"
products List<ProductSummary> Visually matched products.

The standard grid models (pagination, facets, facetUrls, etc.) are not set for visual search results — Discovery does not return facets or pagination for image-based queries.

When no imageId is present the component behaves normally (dataSourceMode = "search").

Server-side proxy endpoints

The plugin exposes two endpoints under /_brxdis-api/visual-search/ via BrxdisVisualSearchPipeline. The /_brxdis-api path is the standard mount name — see Mount placement below for how to wire it. These endpoints are called by the browser; you do not call them from Java.

POST /{widgetId}/upload

Uploads an image and returns the imageId.

Request: multipart/form-data with a field named image.

Response:

{
  "imageId": "abc123",
  "objects": [
    { "id": 0, "bbox": [0.1, 0.2, 0.5, 0.8], "objectType": "shoe" }
  ],
  "results": []
}
Field Description
imageId Opaque ID to pass as ?imageId= on the results page redirect.
objects Detected objects in the image. Each has an id (integer) you can pass as ?objectId= to narrow results to that object.
results Always empty in the current implementation; products come from the grid component.

GET /{widgetId}/search

Fetches products for an already-uploaded image. Called by HstDiscoveryService.visualSearch() on the server side during grid component render — not called directly by the browser.

Query param Required Description
imageId yes Image ID from the upload response.
objectId no Narrows results to a specific detected object.
rows no Number of results. Defaults to the pageSize component parameter.

Mount placement

BrxdisVisualSearchPipeline must be mounted under the channel mount that carries DiscoveryChannelInfo. This is required so the resource resolves per-channel credentials correctly: the pipeline walks the mount parent chain until it finds a mount with DiscoveryChannelInfo, then reads discoveryAccountId, discoveryDomainKey, etc. from it.

Correct — /_brxdis-api nested under the channel mount (credentials resolve from the channel):

/commerce:
  jcr:primaryType: hst:mount
  hst:mountpoint: /hst:site/hst:sites/commerce
  hst:namedpipeline: resourceapi
  /_brxdis-api:
    jcr:primaryType: hst:mount
    hst:ismapped: false
    hst:types: [rest]
    hst:namedpipeline: BrxdisVisualSearchPipeline

This mounts the endpoints at {site}/commerce/_brxdis-api/visual-search/{widgetId}/upload, which the browser reaches via the standard /_brxdis-api context-relative path generated by DiscoverySearchInputComponent.

Incorrect — mounted at host root, sibling of your channels:

# Do NOT mount /_brxdis-api at the host root — there is no channel context here
/hst:root:
  /_brxdis-api:   # ← wrong: BrxdisVisualSearchPipeline finds no DiscoveryChannelInfo in parent chain
    hst:namedpipeline: BrxdisVisualSearchPipeline

When mounted at the root, resolveConfigForRequest() finds no DiscoveryChannelInfo in the parent chain and silently falls back to the global env/JCR credentials — per-channel credential overrides are ignored.

Update your frontend proxy to route /_brxdis-api/visual-search/** to the correct upstream:

// Next.js route.ts (or equivalent)
const upstream = new URL(`${base}/commerce/_brxdis-api/visual-search/${widgetId}/upload`);

SPA / headless integration

The models on both the search input and the search grid components follow the standard Page Model API contract.

Search input — wire the camera button yourself using the model values:

const { visualSearchEnabled, visualSearchUploadUrl, visualSearchWidgetId } = searchInput.getModels();

if (visualSearchEnabled && visualSearchUploadUrl) {
  // show camera button
  // on click: POST image to visualSearchUploadUrl
  // on success: redirect to resultsPage?imageId={id}&widgetId={widgetId}
}

Search grid — detect visual search mode and suppress facet/pagination UI:

const { dataSourceMode, products } = searchGrid.getModels();

if (dataSourceMode === 'visual-search') {
  // render products only — no facets, no pagination, no did-you-mean
}

Object-level refinement (advanced)

When the upload response includes objects, you can present each detected object as a clickable region so the shopper can narrow to “search for shoes” vs. “search for handbag” in the same photo. Pass the chosen object's id as ?objectId= alongside imageId= in the results page URL.

The current bundled brxdis-search-input.ftl does not implement object selection UI — that is left to integrators. The server-side plumbing (objectId is forwarded to the Pathways API) is in place.

Troubleshooting

Symptom Likely cause
Camera button not visible discoveryVisualSearchEnabled is false, or discoveryVisualSearchWidgetId is blank. Check Channel Settings.
Upload returns 400 Invalid or missing widget ID in the URL path. Ensure the widget ID in Channel Settings matches a widget in your Discovery Dashboard.
Upload succeeds but results page shows keyword search imageId URL param is present but widgetId param is missing or blank. Check the redirect URL constructed by brxdis-search-input.ftl or your custom frontend.
Visual search returns empty results The widget may not be trained yet, or the image has no recognisable products. Check the Discovery Dashboard for widget status.
authKey missing warning in logs Visual search requires v2 Pathways API credentials. Set discoveryAuthKeyEnvVar in your Discovery config — see 12-credential-injection.md.
Upload succeeds but uses wrong account / wrong credentials BrxdisVisualSearchPipeline is mounted at host root instead of under the channel mount. No DiscoveryChannelInfo is found in the parent chain so the resource falls back to global env/JCR credentials. Move the /brxdis mount to be a child of your channel mount — see Mount placement above.
